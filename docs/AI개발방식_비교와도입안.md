# AI 개발 방식 비교와 도입안

> 공개용 스냅샷 안내: 첨부 원문·실행 증거·개인 준비 정보·원 저장소 Git 이력은 포함하지 않습니다. 아래 과거 해시와 비공개 출처 경로는 당시 작업 이력입니다. 현재 상태는 [README](../README.md)와 개발 진행을 따릅니다.

2026-10-13 조사·실험. 현재 제품 기준: 웹 데모 복원 커밋 `14d6c91`.

## 결론

현재 방식이 최적이라는 근거는 없다. 다만 요구사항 확인, 작은 단위 구현, 테스트 우선, 별도 에이전트의 검토·검증은 이미 갖췄다. 공개 방법론을 통째로 설치해도 상당 부분이 겹친다.

우선 보강할 것은 **사용자 설명에서 합격 기준을 만들고, 그 기준이 잘못된 구현을 실제로 걸러내는지 검사하는 절차**다. 다음으로 실행 기록을 비교해 개발 방식 자체를 개선한다. 새 에이전트 수보다 업무 해석 오류·수정 부담·실행 비용을 줄였다는 증거가 중요하다.

첫 조사에서 외부 사례, 일정 결정 권한 실험, 후속 비교 계획을 정리했다. 이어 사용자가 원문 근거·검사 능력 점검·실패 재사용 세 절차의 적용을 지시해 `AGENTS.md`, 프로젝트 스킬, 세 역할 지침에 반영했다. [실패·재검사 기록](업무검증기록.md)도 연결했다. **절차 반영과 효과 입증은 별개다.** AI 개발 방식 간 비교와 현업 검수는 아직 하지 않았다.

반복 절차는 [.agents/skills/bnoc-workflow/SKILL.md](../.agents/skills/bnoc-workflow/SKILL.md)에 둔다. 프로젝트 스킬 위치와 AGENTS의 필수 실행 연결은 [OpenAI의 저장소 스킬 활용 사례](https://developers.openai.com/blog/skills-agents-sdk)와 [공식 스킬 문서](https://learn.chatgpt.com/docs/build-skills)의 구조를 참고했다. 자동 호출을 허용하고, 목록 표시와 무관하게 AGENTS에서 정확한 경로로 읽도록 했다. 현재 앱에서의 자동 목록 갱신은 별도 확인 대상이다.

## 대회에서 입증해야 할 것

[대회 안내](대회정보.md) §5에 따르면 완성도 50점, AI 활용도 30점, 차별성 15점, 발표 5점이다. AI 항목은 AI 생성 코드 활용의 정도와 수준을 평가하지만 상세 산정식은 제공되지 않았다. 특정 도구나 에이전트 수로 만점을 보장할 수 없다.

같은 안내 §8은 주요·추가 기능별 AI 코딩 활용 여부, 입력 프롬프트, 활용 소스코드를 별도 파일로 제출하도록 한다. 따라서 “AI로 많이 만들었다”는 설명을 넘어, **실제 지시 → 채택 코드 → 검증 결과 → 사람의 판단**을 기능 하나씩 따라갈 수 있어야 한다. 이는 제출 근거를 강화하기 위한 제안이지 추가된 공식 채점 항목이 아니다.

개발 방식 연구는 짧게 검증하고 제품 개발에 사용한다. 연구만 늘려 완성도 50점에 필요한 핵심 기능 개발을 늦추면 목적에 맞지 않는다.

## 이전 실패에 맞춘 보강

기존 [개발 계약](../AGENTS.md)에는 계약 확인 담당, 구현자, 독립 검토자와 검증자가 이미 있다. 부족했던 것은 모든 역할이 참고하는 **업무 정답의 근거**였다.

폐기 전 보존본에서는 같은 일정 필수화가 한 곳에는 확정 요구사항, 다른 곳에는 검토 대기 제안으로 기록됐다. 시험도 ‘예정일이 없으면 오류’를 기대하도록 바뀌었다. 코드와 시험이 일치해도 잘못된 업무 규칙을 통과시킬 수 있는 상태였다. 보존본은 원인 조사 자료이며 현재 개발 명세로 사용하지 않는다.

현재 복원 명세는 작업반의 일정 입력과 일정 미정을 허용한다. 사용자도 BNOC·사지센은 구체 작업 예정일을 정할 수 없고 작업 부서가 정한다고 설명했다. 요청자의 희망 일정과 작업 부서의 실제 작업 일정을 구별해야 한다. [요구사항 §4·§6](../요구사항.md)

사용자 요청으로 반영한 절차는 기존 역할에 다음 책임을 보강한다.

1. **업무 근거 확인:** 구현 전에 누가, 언제, 무엇을 입력·변경하는지 원문과 비교한다. 사용자 결정·기존 명세·AI 제안을 구분한다. 기존 자료로 해결되는 내용은 다시 질문하지 않는다.
2. **독립적인 합격 기준:** 코드 구현 전 정상 사례와 금지 사례를 정한다. 구현자가 편의상 기대값을 바꾸면 완료할 수 없다. 기준 변경이 필요하면 근거와 변경 이력을 따로 남긴다. 별도 검증자는 구현자 요약뿐 아니라 원래 사용자 결정을 직접 읽는다.
3. **검사 자체의 점검:** 중요한 업무 규칙은 복사본에 대표 오류를 넣어 검사가 실패하는지 확인한다. 오류를 심어도 전부 통과하면 검증이 충분하다고 보고하지 않는다. 작은 문구 수정마다 이런 실험을 반복하지는 않는다.
4. **한 기능씩 구현·수정:** 기존 모듈별 작성자 한 명 원칙을 유지한다. 검토자는 업무 일치 여부와 코드 품질을 나눠 보고, 검증자는 실제 명령과 화면 결과를 남긴다. 정해진 수정 상한을 넘기면 남은 실패와 원인을 보고한다.
5. **완료 근거 보존:** 실제 입력 프롬프트, 채택·폐기한 변경, 실행 결과, 기능 화면, 사람의 수정 의견을 해당 커밋에 연결한다. 프롬프트를 나중에 그럴듯하게 재작성하지 않는다. 원본 대화에 민감 정보가 있으면 공개용에서 제거 사실을 표시한다.
6. **다음 작업에 반영:** 놓친 오류를 재검사 항목으로 남기고, 추가한 절차가 효과가 있었는지 비교한다. 작업 종료마다 완료 범위와 미실행 사항을 기록하고 커밋한다.

시험 통과와 현업에서 쓸 수 있다는 판단은 별개다. 사용자에게는 기능 전체를 설명하게 하기보다, 자료로 결정할 수 없는 업무 지점과 실제 화면에서 확인할 시나리오만 제시한다.

## 실제로 실행한 작은 실험

질문은 하나다. **“BNOC가 작업 부서의 일정을 대신 확정하는 오류를 기존 시험이 잡는가?”**

정상 원본과 오류를 넣을 복사본을 각각 임시 폴더에 만들었다. 두 번째 복사본만 배정 시 고정 일정이 자동 입력되도록 변경했다. 이는 과거 ‘예정일 필수화’와 같은 권한 문제를 겨냥한 인공 결함이며, 폐기된 백엔드 오류를 그대로 재현한 것은 아니다.

| 실행 대상 | 기존 단위 시험 | 원문 근거로 추가한 검사 3개 |
|---|---:|---:|
| 정상 복사본 | 27개 통과 | 3개 통과 |
| BNOC 일정 자동 입력 오류를 넣은 복사본 | 27개 통과 | 2개 통과, **일정 자동 입력 금지 검사 1개 실패** |

추가 검사는 날짜 없이 배정 가능, 작업반의 일정 입력 가능, BNOC의 작업반 일정 수정 불가를 확인한다. 오류 복사본에서 의도한 assertion으로 실패했으며, 문법 오류나 실행 불능을 탐지 성공으로 세지 않았다. 제품 소스 전체의 전후 해시도 일치했다.

독립 검증자가 새 임시 폴더에서 재실행해 같은 결과와 제품 소스 41개 불변을 확인했다. 별도 검토자는 계약·출처 주장·증거 해시를 대조했다. 잘못 표기한 명세 절 번호를 고쳤으며 남은 수정 지적은 없었다.

이 결과가 보여주는 것은 **해당 오류 하나를 기존 단위 시험이 놓쳤고, 보강한 검사가 잡았다는 사실**이다. 검사와 오류를 같은 조사에서 선정했으므로 탐색적 점검이다. 독립적인 AI 비교 실험, 개발 속도 향상, 다른 오류의 예방률을 입증하지 않는다. 브라우저 시험의 탐지력도 이번에는 평가하지 않았다.

## 다음 비교와 채택 기준

다음은 **보강 전 방식과 이번에 반영한 방식을 같은 조건으로 비교**하는 단계다. 기준선은 `5863eca`의 AGENTS 작업 순서이며 계약 확인·테스트 우선·독립 검토·검증을 유지한다. 양쪽에 같은 최신 업무 자료를 주고 과거 문서 참조 오류는 모두 정정한다. 보강 쪽에만 정답 정보를 더 주거나 기준선의 검토를 제거하지 않는다.

첫 선별은 업무 규칙 보존, 실패·재시도, 화면·권한에 관한 작은 작업 3종을 두 방식으로 수행하는 6회로 제한한다. 현재 확정된 동작에서 고르고 제품 원본과 분리한다. 미정인 부대 업무를 실험용으로 발명하지 않는다. 같은 시작 코드·원자료·모델·추론 설정·전체 에이전트 합산 예산을 사용한다. 수행 순서는 교대하고 평가자는 방식 이름을 가린 결과부터 확인한다.

측정할 것은 잘못된 업무 변경을 통과시킨 수, 올바른 결과를 잘못 거절한 수, 합격 여부, 사람 수정 횟수, 실제 소요 시간·사용량, 증빙 누락이다. 시간 제한을 넘긴 실패도 결과에 포함한다. 사용량을 얻지 못하면 추정값을 실측처럼 쓰지 않는다. 독립 실행 환경·초기화·합격 검사 보호와 세부 예산은 실행 전에 고정한다.

제안한 1회 상한은 15분·수정 재검증 2회다. 후보가 중대한 업무 위반을 통과시키지 않고 불필요한 차단과 근거 오류를 늘리지 않으며 사전에 정한 추가 비용 안에 들어오면 잠정 채택한다. 둘 다 전부 맞거나 후보가 느리기만 하면 개선이 입증되지 않은 것으로 처리한다. 6회는 선별이며, 유리한 결과가 나와도 새 작업에서 반복해야 한다. 통계적 우월성이나 ‘최적’이라는 표현은 쓰지 않는다.

## 심사위원에게 보여줄 방식

발표에서는 한 기능을 골라 실제 사용자 요구, AI가 만든 변경, 검증에서 잡힌 문제, 수정된 코드, 작동 화면까지 이어서 보여주는 구성이 적합하다. 기능을 만든 결과와 AI를 통제한 과정을 함께 확인할 수 있다.

예를 들어 일정 기능에서는 “접수 부서가 작업 일정을 정하지 않는다”는 업무 설명 옆에, 잘못된 변경을 잡는 검사와 작업반이 일정을 저장하는 화면을 보여줄 수 있다. 오류 주입 장면은 **실험용 복사본**이라고 명확히 표시한다. 이후 방식 비교에서 개선이 확인되면 오류 통과 건수·사람 수정 횟수·소요 시간을 함께 제시한다. 지금은 그 비교 수치를 채우지 않는다.

현재 확보한 것은 외부 조사, 검사 능력 점검 증거, 세 절차를 반영한 개발 지침·스킬이다. 실제 AI 개발 방식 비교, 백엔드 적용, 부대 운영 기능의 현업 검수, 발표용 기능 화면 묶음은 후속 작업이다.

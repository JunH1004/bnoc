## 2. 비식별 처리

원본에 보이는 실명, 계급과 성명 조합, 연락처, 실제 소속, 요청 제목, 운영 수치, 날짜별 실적은 기록하지 않았다. 이 문서는 원문 전사가 아니라 요구사항 도출에 필요한 일반화 요약이다.

원본 PDF는 요구사항 근거 확인용이다. 공개 자료나 시연 데이터로 사용하지 않는다.

## 3. 현행 화면에서 확인한 기능

### OBS-001 요청 등록

- 요청자 소속, 계급, 성명, 연락처를 입력한다.
- 제목, 관련 근거, 요청 분류, 상세 요구사항을 입력한다.
- 요청 분류는 통신 서비스·장비·회의 지원 등 여러 유형을 선택하는 형태다.
- 파일 첨부 기능이 있다.
- 작업 관련 공식 문서를 별도 경로로 보내라는 안내가 있다.

### OBS-002 처리 현황 목록

- 담당 조직, 진행상태, 기간으로 목록을 검색한다.
- 목록에서 요청자 정보, 제목, 상태, 접수·요청·완료 관련 날짜, 처리 담당자를 확인한다.
- 대기, 접수, 진행, 완료, 분류, 기각으로 보이는 처리 구분이 있다.
- 페이지 이동과 검색·내보내기로 보이는 도구가 있다.

### OBS-003 요청 상세와 처리 입력

- 요청 내용과 분류를 상세 조회한다.
- 처리 담당자는 의견, 처리 가능 여부, 예상 소요기간, 진행상태, 완료일을 입력한다.
- 첨부파일을 확인한다.
- 요청을 수정하거나 취소하는 동작이 보인다.

### OBS-004 통계

- 기간을 선택한다.
- 조직과 처리상태를 교차한 건수 표를 확인한다.

### 화면만으로 확정할 수 없는 것

- 실제 권한 구조와 인증 방식
- 상태가 바뀌는 정확한 조건
- 전화·대면·공식 문서로 받은 요청의 등록 책임자
- 여러 작업반이 함께 처리하는 방법
- 알림 전달 방식
- 첨부파일과 공식 문서의 보안 규칙

## 4. 설문 질문 디지털화

1. 주 연락 경로 외에 어떤 방식으로 업무를 전달받는가?
2. 작업 요청을 처음 받을 때 어떤 정보를 중요하게 확인하는가?
3. 요청 뒤 추가 확인이 필요한 정보는 무엇인가?
4. 요청부터 완료까지 작업을 어떻게 관리하는가?
5. 일정을 어떻게 정하고 변경을 어떻게 공유하는가?
6. 진행상태를 구분해 관리하거나 전달하는가?
7. 완료 시 어떤 정보를 기록하는가?
8. 작업 중 다른 사람에게 재확인하거나 연락하는 경우는 무엇인가?
9. 요청과 진행상황을 한 화면에서 볼 때 먼저 보고 싶은 정보는 무엇인가?
10. 업무 중 직접 입력 가능한 정보의 수준은 어느 정도인가?
11. 현재 요청·진행·상황 공유 과정의 불편과 개선점은 무엇인가?
12. 요청자가 직접 연락할 때 어떤 내용을 문의하는가?
13. 담당 밖 업무나 다른 담당자의 업무는 어떻게 처리하는가?
14. 사용자지원체계 개선 시 추가 고려사항은 무엇인가?

## 5. 설문 근거 카드

### E-001 여러 접수 경로

- 근거 위치: R-01~R-18의 Q1.
- 반복 응답: 전화, 직접 방문, 공식 문서, 전자우편·메시지, 기존 사용자지원 경로.
- 해석: 웹 요청만 관리하면 실제 업무 일부가 기록 밖에 남는다.
- 요구 후보: 비웹 경로로 받은 요청을 권한 있는 담당자가 대신 기록.

### E-002 최초 확인 정보

- 근거 위치: R-01~R-18의 Q2.
- 반복 응답: 요청 내용·증상, 위치, 장비·체계 종류, 요청자와 연락수단, 희망 시간, 긴급성, 관련 문서·근거.
- 해석: 자유 서술만으로는 담당 판단과 방문 준비가 어렵다.
- 요구 후보: 공통 필수값과 업무 유형별 추가값 분리.

### E-003 추가 확인과 수정

- 근거 위치: R-01~R-18의 Q3.
- 반복 응답: 애매한 증상, 실제 작업 희망시간, 장비 식별정보, 지원 가능 범위, 담당 조직 여부를 전화나 대면으로 재확인.
- 해석: 수정 요청과 답변을 기존 요청 기록에 연결할 필요가 있다.
- 요구 후보: 수정 요청, 요청 수정, 확인 이력.

### E-004 분산된 작업 관리

- 근거 위치: R-01~R-18의 Q4.
- 반복 응답: 개인 메모, 종이, 화이트보드, 스프레드시트, 프레젠테이션 일정표, 인수인계 기록, 전화·메시지로 관리. 별도 기록이 없다는 응답도 있음.
- 해석: 같은 작업의 최신 상태와 담당자를 한곳에서 확인하기 어렵다.
- 요구 후보: 단일 작업 원장, 담당자, 일정, 상태, 메모, 변경 이력.

### E-005 일정 결정과 변경 공유

- 근거 위치: R-01~R-18의 Q5.
- 반복 응답: 요청자와 협의, 공식 문서, 상급 담당자 지정, 장비·인원 가능시간을 기준으로 결정. 변경은 전화, 메시지, 내부 기록 수정으로 공유.
- 해석: 일정 변경이 작업 기록과 분리되면 누락 가능성이 있다.
- 요구 후보: 일정 등록·변경, 변경 사유, 관련자 통지.

### E-006 진행상태 사용 편차

- 근거 위치: R-01~R-18의 Q6.
- 반복 응답: 완료 여부만 관리, 상태를 따로 관리하지 않음, 예정·진행·완료 수준으로 관리가 혼재.
- 해석: 상태 수를 늘리기보다 각 역할이 실제 갱신할 최소 상태를 정해야 한다.
- 요구 후보: 짧고 명확한 상태 체계와 가능한 다음 행동 표시.

### E-007 완료 기록 편차

- 근거 위치: R-01~R-18의 Q7.
- 반복 응답: 별도 기록 없음, 인수인계·행정 기록, 작업 결과와 특이사항 기록이 혼재.
- 해석: 완료의 증거와 이후 유사 장애 참고자료가 일관되지 않다.
- 요구 후보: 완료 처리자·완료시각 자동 기록과 선택적인 짧은 완료 메모.

### E-008 협업과 의존 작업

- 근거 위치: R-01~R-18의 Q8.
- 반복 응답: 다른 정비 분야, 상급 담당자, 요청자, 외부 지원조직과 확인이 필요. 장비·회선·회의 지원처럼 둘 이상 분야가 연결되는 경우가 있음.
- 해석: 한 요청을 한 작업반에만 고정하면 인계와 병행 작업이 가려질 수 있다.
- 요구 후보: 동등한 복수 작업반 배정, 작업반별 진행상태와 짧은 메모.

### E-009 한 화면에서 필요한 정보

- 근거 위치: R-01~R-18의 Q9.
- 반복 응답: 작업 내용, 날짜·시간, 위치, 장비·체계, 요청자·연락수단, 담당자, 상태, 과거 처리 여부.
- 해석: 목록과 상세 화면의 정보 우선순위가 명확해야 한다.
- 요구 후보: 핵심 요약 목록과 세부정보 분리.

### E-010 입력 부담

- 근거 위치: R-01~R-18의 Q10.
- 반복 응답: 상태만 입력 가능, 상태·일정까지 가능, 상태·일정·짧은 메모까지 가능이 혼재. 별도 입력이 어렵다는 응답도 있음.
- 해석: 긴 보고서를 매 단계 요구하면 현장 갱신률이 낮아질 수 있다.
- 요구 후보: 단계 변경은 최소 입력, 상세 기록은 필요한 시점에만 요구.

### E-011 현재 불편

- 근거 위치: R-01~R-18의 Q11.
- 반복 응답: 여러 채널의 중복 전달, 늦은 공유, 담당 불명확, 검색 어려움, 필요한 정보 누락, 기존 화면 사용성, 알림 부족.
- 해석: 새 제품의 핵심 가치는 기능 수보다 기록 일원화와 최신성이다.

### E-012 요청자 직접 연락

- 근거 위치: R-01~R-18의 Q12.
- 반복 응답: 신규 요청, 오류 증상, 추가 요구, 가능 여부, 일정 문의, 진행 확인.
- 해석: 요청 수정과 추가정보 전달, 상태 조회가 필요하다.

### E-013 담당 밖 업무 처리

- 근거 위치: R-01~R-18의 Q13.
- 반복 응답: 적정 담당 연락처 안내, 다른 부서로 전달, 조정 담당에게 반환, 상급 담당자에게 보고.
- 해석: 무응답 종료가 아니라 사유 있는 반환·이관·재배정 흐름이 필요하다.

### E-014 개선 아이디어

- 근거 위치: R-01~R-18의 Q14.
- 반복 응답: 검색, 업무 유형 구분, 웹 기반 양식, 알림, 진행상황 공유, 과거 작업 조회, 간단한 입력.
- 해석: 요구사항 우선순위 후보로 사용하되, 단일 응답의 제안은 자동 채택하지 않는다.

### E-015 사용자 확인: 요청 등록 경로

- 근거 위치: 사용자 답변, 2026-09-20.
- 기본 흐름: 요청자가 필요한 지원을 직접 등록한다.
- BNOC 대리 등록: 요청자가 필요한 도움을 스스로 특정하지 못해 전화로 문의하거나, 인트라넷 컴퓨터·회선 장애로 체계에 접속할 수 없는 경우 BNOC가 대신 등록한다.
- 작업반 후보고 등록: 긴급 요청이 작업반에 직접 전달되면 작업반이 먼저 조치한 뒤 요청과 조치결과를 등록한다.
- 요구 후보: 요청자와 BNOC는 같은 요청 기록을 사용하고 실제 등록자는 자동 기록한다. 작업반 선조치 후보고는 별도 등록 행동으로 제공한다.

### E-016 사용자 요구사항 검토: 단순화와 계정정보

- 근거 위치: 사용자 답변, 2026-09-20.
- 작업 담당자와 작업 책임자를 별도 역할로 나누지 않는다.
- 목표 운영환경에서는 공군 인트라넷 계정으로 로그인하고 이름·군번·소속·계급을 계정에서 가져온다. 대회 결과물은 이를 인터넷에서 시연하는 웹 데모다.
- 요청자 연락처와 실제 정비 대상자의 연락처는 다를 수 있다.
- 요청자 등록과 BNOC 등록은 같은 요청이며 별도 요청 유형으로 나누지 않는다.
- 복수 작업반 배정에 주·부 구분을 강제하지 않는다.
- 작업 중에는 짧은 메모면 충분하다. 완료 입력도 최소화한다.
- 요청자에게 보이는 상태는 `대기`, 선택적 `문서 대기`, `배정`, `작업 중`, `완료` 중심으로 압축한다.
- 작업반 내부 상태는 `배정`, `작업 중`, `완료`, `반환`으로 단순화한다.
- 모든 배정 작업은 완료 대상이다. `작업 집합`, `필수 작업` 같은 별도 개념을 사용하지 않는다.
- 일정 지연·외부 대기·긴급도·우선순위·완료 확인을 별도 상태나 단계로 만들지 않는다.
- 요청 수정·취소·재개를 허용하고 별도 `종결` 개념은 두지 않는다. (재개는 이후 E-020에서 제거)
- 모바일 사용 요구는 두지 않는다.

### E-017 사용자 확인: 알림·첨부·보존·이관

- 근거 위치: 사용자 답변, 2026-09-20.
- 알림은 필요하다. 전자우편 등 체계 밖 경로가 아니라 체계 내부 알림이면 된다.
- 파일 첨부 기능은 필요하다.
- 완료·취소된 요청과 변경 이력은 삭제하지 않고 계속 보존한다.
- 현행 사용자지원체계의 데이터는 새 체계로 이관하지 않는다.
- 요구 후보: FR 수준의 체계 내부 알림, 첨부파일 저장·조회, 무기한 보존 정책.

### E-018 사용자 확인: 신송 기능 미채택

- 근거 위치: 사용자 답변, 2026-09-20.
- 별도 신송(인수인계) 기능은 만들지 않는다. 기존 작업 이력과 메모로 대신한다.
- 해석: DEC-003에서 정의한 신송 개념은 유지하되 제품 기능으로는 채택하지 않는다.

### E-019 사용자 확인: 웹 데모 계정 범위와 실제 요청자 표기

- 근거 위치: 사용자 답변, 2026-09-20.
- 대회 웹 데모는 BNOC(사지센)·요청자·작업반 세 역할의 시연 계정만 제공한다. 권한 관리자 역할은 이번 데모 로그인 범위에 포함하지 않는다.
- BNOC 대리 등록과 작업반 선조치 후보고에서 실제 요청자는 계정을 조회해 지정하지 않고 자유 텍스트로 입력해 기록한다. 대부분 요청자 본인이지만 문서화된 값은 텍스트일 뿐 계정과 연결하지 않는다.

### E-020 사용자 확인: 요청 수정·취소 범위와 재개 제거

- 근거 위치: 사용자 답변, 2026-09-20.
- 요청 수정은 배정된 작업이 `작업 중`이 되기 전까지만 허용한다. 작업이 시작된 뒤에는 요청자가 직접 수정할 수 없다.
- 취소는 상태와 무관하게 언제든 가능하다. 진행 중이던 작업을 정지시키는 것과 같은 개념이며 취소 뒤 처리를 별도로 복잡하게 만들 필요는 없다.
- `재개`는 용도가 불분명하므로 상태·행동 목록에서 완전히 제거한다.

### E-021 사용자 확인: 요청 분류별 입력값 차이

- 근거 위치: 사용자 답변, 2026-09-20.
- 모든 요청에 장비·체계 정보가 있는 것은 아니다. 예: 화상회의·일반회의 지원 요청은 장비 정보가 없을 수 있다.
- 해석: 장비·체계 종류를 모든 요청의 공통 필수값으로 두면 회의 지원처럼 장비가 없는 요청을 등록할 수 없다. E-002가 제시한 "공통 필수값과 업무 유형별 추가값 분리" 요구 후보와 일치한다.
- 요구 후보: 요청 분류(OBS-001의 통신 서비스·장비·회의 지원 등)를 공통 필수값으로 두고, 장비·체계 종류는 분류가 장비 관련일 때만 필수로 요구하는 조건부 필수값으로 다룬다.

### E-022 사용자 확인: 요청 유형별 세부 분류 체계

- 근거 위치: 사용자 답변, 2026-09-20.
- 장비·체계가 있는 요청: 체계 종류(인트라넷·인터넷·AFCCS·KJCCS·기타), 자원 유형(회선·전화·PC·기타), 작업 유형(신설·고장·지원·이전·기타) 세 값을 함께 기록한다.
- 장비·체계가 없는 요청: 회의 유형(화상회의·일반회의·기타) 한 값만 기록한다.
- 해석: 요청 분류는 단일 평면 목록이 아니라 요청 유형(장비/체계 또는 회의 지원)에 따라 갈라지는 다차원 분류다. E-008이 언급한 "장비·회선·회의 지원"의 구분과 OBS-001의 "통신 서비스·장비·회의 지원 등"이 이 구조 안에서 모두 설명된다.
- 요구 후보: DEC-028 확정. FR-006 세부 구조 반영.

### E-023 사용자 확인: 정비대상자 정보 구성

- 근거 위치: 사용자 답변, 2026-09-20.

- 해석: 계정에서 자동으로 가져오는 요청자 신원 구성요소(이름·군번·소속·계급, DEC-022)와 같은 원칙을, 계정이 없는 정비대상자에게는 수기 입력으로 동일하게 적용한다.

## 2026-10-13 설계 재개에서 확정된 업무

출처는 현재 대화의 사용자 답변이다. 기존 설문 응답·화면 관찰로 바꿔 기록하지 않는다. 이 결정 뒤 사용자가 설계 0.7 구현을 승인했다. 현재 구현·검증·후속 개선 상태는 [개발 진행](개발진행.md)을 따른다.

- 일반/긴급: 배정 후 BNOC 정정 가능, 반환 재배정은 기존 분류 유지. 완료 후보고는 승인 없이 미분류 등록 후 BNOC 사후 분류.
- 요청 내용 자체가 작업지시. 작업반이 자기 반 명부에서 담당 인원을 선택. 반장 지정은 제거 유지. 새 담당 인원 필수 완료 조건을 추가하지 않음.
- 각 부서 담당자가 자기 명부·병력·야간 현황 관리. 병력은 선택 날짜, 야간은 근무 시작일, 과거 입력·수정 허용. 모든 부서 상호 조회이며 일반 요청자까지 새 조회 확대를 추론하지 않음.
- GPS/CPCON은 모든 로그인 사용자 조회. 공지는 전체 로그인 조회를 유지하고 BNOC 계정이면 누구나 제목·본문·첨부 수정. 게시 종료·숨김·확인 기능 없음.
- 직접 받은 일은 완료 후 기존 후보고로 등록. 미완료 별도 등록·BNOC 전달·자동 역할 전환 없음. 모든 유효 작업이 현재 배정이면 본인 비취소 요청 수정 가능.
- 공개 자료로 알 수 있는 사실·일반 화면 동작·기술값은 AI가 조사·판단한다. 군 내부 업무 의미만 질문하며 이미 답한 내용은 다시 묻지 않는다. 임시 단계 A/B·가짜 이름·합성 계급 금지.

**기술 설계안:** 별도 사전의 코드 1~5를 CPCONⅠ급~Ⅴ급으로 표시한다. 한국어 태세명·시험 단계 A/B를 만들지 않으며 GPS의 5=양호를 붙이지 않는다. 적용 범위는 정보원의 scopeKey로 분리 관리하고 실제 부대명을 생성하지 않는다. 화면에는 GPS 정보원·CPCON 정보원과 원본 시각·실패/오래됨을 표시한다. 모의 구현 구분은 기술 문서·설정·내부 sourceMode에 보존한다. 공개 자료의 사실과 대회용 표시/검증 기술안을 구별한다.

# AI 개발 방식 평가 준비

이 폴더는 개발 방법을 평가하는 실험용이다. 제품 코드·업무 명세·운영 의존성을 변경하지 않는다.

## 첫 실험: 검사가 잘못된 업무 변경을 잡는가

2026-10-13 실행 전에 정한 조건:

- 정답 근거: 사용자가 BNOC·사지센은 구체 작업 예정일을 정할 수 없고 작업 부서가 정한다고 설명했다. 복원 명세의 `요구사항.md`의 웹 데모 기준선 §4, FR-016·018도 작업반의 일정 입력과 일정 미정을 허용한다. 요청자의 희망 일정과 작업반의 실제 작업 일정은 구별한다.
- 정상 대조군: 현재 `frontend/src` 원본의 임시 복사본.
- 결함 대조군: 다른 임시 복사본에서 BNOC 배정 시 작업 일정이 자동 확정되도록 한 줄만 변경.
- 비교: 각 복사본의 기존 단위 시험과 원문 근거로 작성한 일정 검사. 정상 입력은 통과하고 잘못된 일정 확정은 실패해야 한다.
- 오류 탐지는 의도한 assertion에서 실패한 경우만 인정한다. 문법 오류·실행 실패를 탐지 성공으로 세지 않는다.
- 임시 복사본만 수정하며 종료 시 제거한다. 원본 소스 해시를 전후 대조한다. 원본 시험은 수정하지 않는다.
- 이번 실험은 **검사 능력 점검**이다. AI 개발 방식 간 A/B 실험, 생산성 향상, 오류 예방률, 현업 검수 완료의 증거가 아니다.
- 정상 대조군과 결함 1개만으로 다른 결함까지 탐지한다고 일반화하지 않는다. 기존 브라우저 시험 전체의 탐지력을 평가하는 실험도 아니다.

실행:

```bash
node experiments/ai-workflow/run-sensitivity.mjs
```

실행별 로그·결과·소스 해시는 `.local/ai-workflow-sensitivity/` 아래 새 폴더에 보존한다. `run-sensitivity.mjs`는 네 하위 실행의 예상 결과까지 확인하며 조건이 다르면 실패한다.

2026-10-13 워크플로우 반영 후에는 정상 복사본의 기존·계약 검사 통과와 오류 복사본의 의도한 계약 검사 실패를 필수로 확인한다. 오류 복사본의 기존 시험 결과는 관찰값이다. 향후 기존 회귀 시험도 오류를 잡으면 실패 결과를 `failed-needs-review`로 남기며 로그로 이유를 확인한다. 이를 실행기 자체 실패나 무조건적인 탐지 성공으로 처리하지 않는다. 과거 `5863eca` 결과는 당시 실행기 기준으로 보존한다.

현재 실행기는 실제 주입 전후 한 줄과 위치를 `mutation.patch`로 보존하고 `summary.json`의 `mutationDiff`로 연결한다.

실행기 변경 검증: `node --test experiments/ai-workflow/run-sensitivity.test.mjs`. 정상, 기존 시험이 같은 오류를 잡는 경우, 정상 기준 자체가 깨진 경우를 각각 임시 복사본에서 확인한다. 관련 실패와 실행 시점은 [업무 검증 기록](../../docs/업무검증기록.md)에 연결한다.

## 이후 실제 개발 방식 비교

비교 A는 보강 전 `5863eca`의 AGENTS 작업 순서인 계약 매핑·test-first·구현·독립 검토·검증이다. 비교 B는 같은 역할에 이번에 적용한 원문 근거 확인, 구현자와 별도로 검토하는 합격 시험, 실패 기록의 재검사, 완료 증빙 확인을 추가한다. 두 방식 모두 동일한 최신 업무 자료를 사용하며 폐기 문서 참조 오류는 양쪽에서 제거한다. 기준선의 기존 검토·검증을 빼서 후보가 좋아 보이게 하지 않는다. 현재 절차 채택과 효과 비교는 별개이며 비교 실행은 아직 하지 않았다.

첫 선별은 작업 3종 × 두 방식으로 6회. 업무 규칙 보존, 저장 실패·재시도, 화면과 권한을 각각 포함하되 실제 작업의 합격 기준은 개발 범위 확정 뒤 고정한다. 각 실행은 같은 시작 커밋·모델·추론 설정·시간/토큰 상한을 사용하고, 두 방식의 실행 순서를 교대한다. 각 방식의 모든 하위 에이전트 비용을 합산한다. 시간·사용량을 확보하지 못하면 미측정으로 남긴다.

1회 상한은 우선 15분·수정 재검증 2회로 제안한다. 실제 실행 전에 고정하며, 시간 초과·실패도 결과에서 제외하지 않는다. 이 설정은 대회 공식 기준이 아니다.

평가자는 실행 방법 이름을 가린 산출물을 먼저 채점한다. 코드 실행과 사람이 확인한 업무 기대값을 우선하며, AI 평가는 보조다. 같은 원문은 양쪽에 제공하고 별도 합격 검사 파일은 구현 작업 폴더 밖에 둔다. 같은 파일시스템의 접근 지침만으로 기술적 격리가 된다고 주장하지 않는다.

지표는 업무 위반 통과 건수, 정상 결과 오탐, 최종 합격 여부, 사람 수정 횟수, 실제 경과 시간, 토큰·비용, 프롬프트·변경·시험·커밋 연결 누락이다. 속도 하나로 채택하지 않는다. 6회는 선별용이며 우월성 입증은 아니다. 후보가 유리하면 새 작업으로 반복하고, 동률이면 더 간단한 현재 방식을 유지한다.
